# 局部异常不冻结成本账本设计

## 目标

修复单个历史会话解析警告导致整个本地成本账本停止更新的问题。保留异常日志与诊断信息，同时让其他可完整解析的会话继续进入 `cost-event-ledger.json`，使 Today、30 Days 和 Lifetime 展示当前已知的有效计费事件。

## 方案比较

### 方案 A：按会话隔离异常并提交有效事件（采用）

- session cache 继续保存逐文件扫描警告，历史记录诊断能力不变。
- ledger 刷新不再以“所有 warning 必须为空”为前提；可解析会话照常增量写入。
- 无法解析或缺少计费模型的会话不进入 ledger，也不覆盖已有 ledger 事件。
- 只有会话目录扫描失败、账本无法初始化或账本无法持久化等全局故障才让成本刷新失败。

优点是故障隔离边界与账本的 session 粒度一致，既不会因一个坏文件冻结全部统计，也不会用猜测模型给异常用量定价。

### 方案 B：自动为缺少模型的会话填入当前模型

可以让所有 Token 都进入统计，但历史会话使用的真实模型无法从日志恢复时会产生错误金额。拒绝采用。

### 方案 C：移动或删除异常 JSONL 后重建

能暂时绕过警告，但会破坏用户的会话历史，而且新异常仍会再次冻结账本。拒绝采用。

## 数据流

1. 扫描所有 session JSONL，生成可解析记录和逐文件 warning。
2. 可解析记录继续执行 fork 基线解析、事件去重和 ledger 增量合并。
3. 异常文件保留 warning，但不参与 ledger 更新，也不删除该 session 已经持久化的旧事件。
4. ledger 成功持久化后，从新 ledger 计算 Today、30 Days 和 Lifetime。
5. 全局扫描或持久化失败时保留上一次已知正确的缓存摘要。

## 准确性边界

- 不猜测缺失模型，不给无法定价的历史事件虚构成本。
- 已有 ledger 事件不会因为源文件后来损坏而被删除。
- 有效会话的新增事件必须继续计入，不能被其他文件的 warning 阻断。
- warning 仍可通过 records 数据源查看，修复不隐藏源数据质量问题。

## 测试

- 先写回归测试：一个缺少模型的异常会话与一个有效会话并存时，有效会话仍进入 ledger，刷新结果可发布。
- 保留已有“损坏源文件不覆盖既有 ledger”测试。
- 覆盖重启后 ledger 仍包含有效新增事件。
